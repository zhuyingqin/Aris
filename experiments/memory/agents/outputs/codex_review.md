## 1. 会明显改变结论的问题

1. **时间边界未锁定。** 前情、重排及触发探针都查全库，后续复述可挤掉金标，也可推高表观命中。踩坑和普通回合按**会话开始**过滤，先开的并行会话仍可能带入后来才出现的修法，更早但同会话的证据却被排除。笔记也用会话开始时间代替可用时间，全库 FTS 仍共享未来统计量。净影响无法从汇总量化。（`eval_recall.py:82`、`rerank.py:23`、`eval_trigger.py:57,75`、`eval_relearn.py:142`、`memlab.py:152,197,395`）
2. **生产基线失真。** Python 漏掉生产的偏好锚点、时间重排和返回窗口。v2 未按层及 `updated_at` 取前 100，未过滤过期，分词把中文标点吞进词里，踩坑的时间过滤还排除了当前会话 R1。注入复刻也省略了模式、确认 R3、远端 R2 和实际渲染限额。漏窗口和词项粘连可压低基线，过期原子和未渲染候选可抬高基线。4%／27% 不能当生产实测。（`memlab.py:105,219,296,308`、`session_index.rs:997,1020,1034,1054,1427,1809`、`research_memory_v2.rs:1149,2493`、`memory.rs:124,442,1662`）
3. **命中口径不齐。** 注入的 Hit@3 实为整组任意命中，偏宽。踩坑笔记按教训 ID 映射，原文按指定工具或修复回合，单独命中报错也算，等价修法却可能漏分。前情统一放宽到源回合 ±1，也会把无答案的邻居计入。69%／66% 衡量的是代理命中，修法或答案真正可用的比例未知。（`eval_relearn.py:55,108,160,180`、`eval_recall.py:63,74`、`report/index.html:59`）
4. **69% 没经过触发门。** 检索评分与触发率分开算。97% 是已标重学事件的触发率，23% 是 35 个反例中的触发率。报告的 4%→69% 同时换了查询时机、文本、存储和范围，无法单独归因给笔记或触发。（`eval_relearn.py:70,148,160,190`、`report/tree.json:310`、`report/index.html:74`）
5. **缓存数据不能证明撤注入省多少。** 71 次匹配全有块，空块对照为 0。分箱靠时间推断换轮，没核验块是否变化。标题的 7% 对 99% 还跨了间隔桶，容易夸大注入代价。（`eval_cache.py:60,107`、`cache.json:6,19`、`make_report.py:35,245`）

## 2. 次要问题

单用户、测试各 52／59 题，报告缺配对区间。前情改写题可能偏词法，重排融合较消息 BM25 的 Hit@3 仅高 1 题，Hit@1 反而下降。普通回合也未标注是否需要历史，触发率不能当误触率。（`report/index.html:84`、`recall_extra.json`、`eval_trigger.py:68`）

## 3. 架构判断

**双通道值得验证。** 原始会话做前情检索有最强的离线信号。教训笔记做踩坑召回有潜力，报错后的实际修复收益待测。撤掉每轮 system 注入值得做对照，报告的「零风险、马上省钱」超出证据。**最弱的是常驻层只收用户确认**，依据主要是历史自动「决定」的误判，缺少对确认质量、遗漏和维护负担的直接比较。（`report/index.html:71,73`、`report/tree.json:374,410`）

## 4. 优先补两个实验

1. **按事件时间滚动回放**，冻结可见语料、索引和笔记版本，运行真实生产基线。盲评实际送达文本能否回答或修复，在同一查询、范围和预算下比较原文与笔记，并把触发门纳入计分。
2. **随机配对比较现状注入与双通道送达**，固定模型、供应商和请求间隔。用真实历史请求和普通回合测回答正确率、重复失败率、误送达率、缓存 token 与总成本。

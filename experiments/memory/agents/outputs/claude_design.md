# SomniQ 记忆模块设计（独立稿）

一句话：**原始会话就是记忆，只需要强检索；常驻层只收用户确认过的条目；送达不改 system prompt 里会变的部分。**

## 1. 诊断

**最该砍**

1. **v2 抽取+晋升管线**（`research_memory_v2.rs` 的 outbox/`record_extractions`/`apply_promotion`，`memory.rs` 的 `spawn_v2_outbox_drain`）。贵（≈5k token/条），且 30% 是错的。根因修不好：长期性只有用户知道，模型只看单个回合判断不了。
2. **每轮拼进 system prompt 的召回块**（`engine.rs:9633/9713`，6,000 字）。默认的 `legacy_r0_only` 下照样注入 R0 片段，而且按用户原话查询，所以每轮都变，后面整段历史的缓存全部失效。
3. **两套弱检索**：`recall_local` 先取最近 100 行再做子串计数，没有 IDF；`recall_terms` 把整句中文当成一个词。`search_like` 对整条消息做二元组 OR，按命中数排序，也没有 IDF。
4. **知识状态机**：把层当 TTL 标签用，再加 `subject_key`、`supersede_same_subject`。P13/P15/P16 都出在这里。
5. **agent 直写常驻层**：`run_memory` 默认不审批，模型能把"用户偏好"直接写进每轮都注入的 USER.md。这是第 1 条的错误换了个入口。

**最该保留**

1. 规范事件日志作为唯一真源。`session_index.rs` 的每项目 SQLite、增量同步、`merge_ranked_lists`（RRF）、embedding 接口都留着。
2. `hot_memory.rs` 的 MEMORY/USER：可读、可手改、按作用域隔离、原子写、有 pending。但要修一个 bug：`joined_chars` 用 `len()` 计字节，2,200"字"对中文只有约 733 字。
3. `tool_episodes_for_turn` + `tool_output_digest`：零 token、确定性，是全仓唯一又便宜又准的写入。需要补一条"恢复必须针对同一目标"的约束。
4. 度量设施：每轮的 `memory_recall` 事件、`usage-log.jsonl` 的缓存字段、`.wire.jsonl` 的完整请求体。§3 的假设都靠它们验证。
5. 边界规则：排除 `wf-*`/`somni-*` 会话、项目隔离、检索结果标为"不可信"、读过外部内容的回合要标记。

## 2. 目标架构

| 环节 | 设计 | 理由 |
|---|---|---|
| 谁写 | ① 代码：工具失败后对同一目标恢复的 episode；② 用户：消息上一键"记住"，或确认候选卡；③ agent 的 `memory` 只能**提议**，USER 和决定/约束类条目一律进 pending | 写的人和批的人分开，这一层的独立审查由用户承担 |
| 何时写 | 回合结束时同步写，不调模型；候选卡在会话结束时集中展示 | 重学事件很少，写入成本必须接近 0 |
| 写什么 | 不抽原子。只写 episode（错误签名→修复调用）和用户确认过的条目，决定本身留在原会话里 | 「B吧」离开上下文就是错的，留在原处才知道它在答什么 |
| 存储 | 真源是 events.jsonl。派生的 `session-index` v3 增加"交换块"：上条助手消息结尾 + 用户消息 + 回复开头，≤500 token，附带失败工具摘要；建 trigram FTS 和 CJK 二元组影子列；`episodes` 表按签名哈希。MEMORY/USER 改成按字符计 | 只有一份真源，其余可删可重建；交换块让短答带上它回答的问题 |
| 检索 | 长词走 trigram、两字词走二元组，各出一路 BM25，RRF 合并，同一会话只留一条，取 top5、每条 ≤600 字。时间只在同分时用来排先后，不衰减。episode 按签名精确匹配。本地 embedding 等 H7 通过再加 | 本地、零依赖；85% 的重学间隔超过 2 天，衰减恰好压掉要找的内容 |
| 送达 | ① 常驻：MEMORY/USER 在会话开始时取快照，会话内逐字不变；② 工具：`session_search` 换新检索器并加 `turn_id` 取原文，不另立新工具；③ 触发：工具报错时按签名查 episode，命中就在这条 tool_result 末尾附 ≤300 字；新会话的首条消息检索一次，超过高阈值才在消息末尾附 ≤800 字 | 内容追加在末尾，只多付这几百 token，不破坏前缀缓存 |
| 整理 | 写入时按规范化哈希去重；同签名的 episode 合并。同签名再次失败、旧修复也无效时标 stale。同签名跨 ≥2 个会话出现，或带"以后/一律/不要再"一类标记的用户话在另一会话里被重申时，生成候选卡，用户确认才写入 | 漏晋升只是多查一次，错晋升会一直污染常驻层，所以不让 LLM 做合并或取代 |

## 3. 可证伪假设

"重学集"指已标注的跨会话重学事件及其证据回合，判定全部离线进行。

| # | 假设 | 对比 | 指标 | 判定线 |
|---|---|---|---|---|
| H1 | 原文检索不比 v2 差 | A：`recall_local` 查 v2 active 原子；B：交换块 BM25，只用事件之前的会话 | 重学集 recall@5 | B≥A 就停 v2 |
| H2 | 召回块是缓存的主要破坏者 | `.wire.jsonl` 里召回块非空的回合 vs 为空的回合 | 与上一请求的字节级公共前缀占比，另看 cache_read 比例 | 非空组中位数 <50%、空组 ≥90% 就撤块；空组也 <90% 说明另有破坏者，先查它 |
| H3 | 注入的内容很少被用到 | `memory_recall` 非空的回合 | 回复或工具参数里出现块内独有、≥8 字片段的回合占比 | <5% 就删注入 |
| H4 | 模型不会主动去查 | 重学集：重新推导之前有没有调用 `session_search` | 主动查询率 | <30% 必须做触发；>70% 只留工具 |
| H5 | 按签名查 episode 又准又有覆盖 | A：签名精确匹配；B：用报错文本做 BM25 | 在跨会话复发的失败上看覆盖率，以及 precision@1（与后来实际用的修复一致） | A 精度 ≥80% 且覆盖 ≥30% 就上线报错触发 |
| H6 | 交换块比单条消息好 | A：单条消息或 400 token 滑窗；B：交换块 | 重学集里"决定类"事件的 recall@5 | B≥A+10pp 才采用 |
| H7 | 本地向量能带来增量 | A：两路 BM25；B：再加一路本地 embedding（3060 离线编码） | recall@5、查询 p95 | +10pp 且 p95≤200ms 才上 |
| H8 | "标记+重申"能挑出真规则 | A：v2 的 R3/决定原子；B：带持久标记、≥2 天后在另一会话被重申（二元组 Jaccard≥0.3） | 50 条人工标注的精度；每周候选数 | B 精度 ≥80%、比 A 高 20pp、每周 ≤5 张卡 |

## 4. 不建议做的三件事

1. **任何让模型判断"长期性"的机制**：LLM 抽取、四题决策门、Jev、蒸馏本地判定器都不做。标签每周只有个位数，而且这个问题模型本来就答不了。
2. **L1 设计的后台补录和"今昨笔记"注入**：它用很重的协议（游标、配额、终态归一）去复述原会话里已有的内容。85% 的重学间隔超过 2 天，今昨窗口最多覆盖 15%。
3. **语义去重、自动取代、TTL、主题键，以及云端向量库**：前几项已被 P13–P16 证明会制造错误；云端向量库违背本地优先，网关也没有 embedding。

## 5. 只做一件事

**关掉自动记忆**：撤掉 `engine.rs:9713` 每轮注入的召回块（包括 R0 片段），把 `memory_v2_mode` 固定为 `legacy_r0_only`。这是删除，不需要新建：每一轮都省下缓存和抽取的 token，改配置就能回滚；损失的只是 ≤5% 回合里或许有用的提示，`session_search` 仍然可用。先用 H2/H3 在旧日志上量化，改完后用同一个脚本复测。

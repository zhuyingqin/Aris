# PDF 生成的技术要点

两份附件都是 A4 分页文档，用 HTML + Chrome 打印生成。以下是实测踩过的坑。

---

## 一、Chromium 下 CSS `counter(page)` 画页码是无效的

**现象**：用 `position: fixed` 元素配合 `counter(page)` 做页眉页脚，是网上通行写法。该元素在 Chromium 打印时确实每页重绘，但 **`counter(page)` 只解析一次**——60 页会全部印成「第 1 页」。

**为什么危险**：HTML 屏幕预览里完全看不出来（屏幕上本就不分页），只能从产出的 PDF 里验。而「页脚标注连续页码」是软著的形式要求，印错必被退回。

**正确做法**：走 DevTools 协议的 `Page.printToPDF`，用 `headerTemplate` / `footerTemplate` 里的 `.pageNumber` / `.totalPages` 占位类。这是唯一能得到真递增页码的机制。`render-pdf.cjs` 已实现，由 HTML 里的 `<meta name="pdf-running" content="on">` 触发。

注意：Chromium **不支持 `@page` 的 margin box**，所以没有纯 CSS 的替代方案。

**验证**：`node scripts/verify-pdf.cjs <pdf> [期望页数]` 会解压 PDF 内容流反查每页页脚的页码字形，确认 1..N 严格递增。**每次生成后都要跑。**

---

## 二、两类文档，两种分页策略

| 文档 | 策略 | 页眉页脚 |
|---|---|---|
| 源程序 | 脚本切成固定高度的 `.page` 容器，每页 50 行 | 逐页写死在容器内，不依赖浏览器 |
| 软件说明书 | 流式排版，页数由内容决定 | 由 `Page.printToPDF` 绘制 |

源程序的页码是生成时算好直接写进 HTML 的，所以不受上面那个坑影响。

---

## 三、源程序的行高与页高必须配平

`.page` 固定 `height: 265mm`，`.code` 是 `flex:1` + `overflow:hidden`。**溢出会被静默裁剪，不会新开一页**——所以「PDF 总页数正确」不能证明每页内容完整。

实测配比（A4，上下边距 16/14mm）：

- 50 行 × `line-height: 4.7mm` = 235mm
- 页眉约 8mm + 页脚约 8mm + 省略声明约 8mm = 24mm
- 265 − 24 = 241mm > 235mm ✓

**带省略声明的那一页（第 31 页）要单独验**，因为它比别的页多一个元素。做法：把该页单独抽成一个 HTML 渲染成单页 PDF，看最后一行是否完整、页脚是否在位。

行宽方面，8pt 等宽字体在 A4 可排约 109 字符。超长行用 `white-space: pre` + `overflow: hidden` 裁掉——实测超过 109 字符的行通常只占 0.4%，可接受。但**单行超过 400 字符的文件整个排除**（多是内嵌 base64 或压缩产物，不具展示性）。

---

## 四、Windows 上 PDF 被占用导致覆盖失败

PDF 阅读器、IDE 预览窗格会持有文件独占句柄，覆盖时报 `EBUSY`。关闭标签页往往也不立即释放。

`render-pdf.cjs` 已内置兜底：先写 `<名>.new.pdf`，再重试替换 6 次；始终替换不掉就保留 `.new.pdf` 并明确提示，不让整批渲染失败。

**看到 `.new.pdf` 提示时要留意**：要提交的是新文件，旧的同名 PDF 是过期版本，别交错。

---

## 五、字体

页眉页脚、正文用宋体（`SimSun`），标题用黑体（`SimHei`），代码用等宽（`Consolas`）。都是 Windows 自带字体，不需额外安装。中文若渲染成方块，检查 HTML 是否声明了 `<meta charset="utf-8">` 且文件本身是 UTF-8 存储。

---

## 六、页数调节

说明书页数不够 60 时，**不要靠加大行距或灌水凑页数**——审查员看得出来。可以加的实质内容：

- 附录：快捷键总表、术语表、内置功能/工具清单、数据目录结构说明
- 典型业务流程示例：把几个模块串成一条完整的使用路径
- 常见问题与故障处理：按模块分类，每条给现象和处理方法

这些都是真实用户手册该有的内容，写出来既凑够页数又提高说明书质量。实测一份完整手册（14 章 + 6 附录）约 53–60 页。

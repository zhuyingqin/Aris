# DOCX 格式编排优化方案

状态：2026-11-11 已补齐公开验收的 13 项原生操作缺口，21 项文件任务通过，2 项协作/全局设置范围外，59 页最终 PDF 全部查看。Open XML SDK 3.3.0 已接入开发验收，无新增结构错误；后台请求衍生与工程回归 9 组通过。完整产品目标仍有 M3/M4 未完成项。

日常办公后续已补齐 8 项原生缺口，14 项自动检查通过，20 页图片观察保留 1 项原件已有的标题字形异常，详见 [日常办公验收](docx-office-acceptance.md)。使用桌面配置及软件共享 Chat runtime 的自然语言任务结果另列在 [Agent 验收](docx-agent-acceptance.md)，不与直接工具测试或 UI/WPS 验证混计。

基线为 SomniQ Studio 0.4.87（e80513eb）。选型依据见 [开源方案核查](docx-open-source-selection.md)，当前范围见 [真实请求衍生验收](docx-user-acceptance.md) 与 [公开任务验收](docx-public-acceptance.md)。WPS 旧候选曾产生纯白第 4 页，本轮修复空段落/段落标记后仅在 LibreOffice 复验，新候选 WPS 兼容仍未验证；按用户要求直接查看 PDF 截图，不进行电脑界面操作。详见 [WPS 记录](docx-wps-compatibility.md)。

目标是让用户在 Chat 中提交 Word 文档或排版要求后，得到符合模板的可编辑 DOCX、可检查的修改记录，以及与最终文件对应的页面验收结果。第一版聚焦研究报告、论文草稿和专利文档常见的字体、段落、标题、表格、图题及公式编排。

## 0.4.87 基线缺口

1. `crates/runtime/src/docx.rs` 的 `DocxTextEdit` 只有段落 id、旧文字和新文字；当前工具保护格式，但不能显式改变段落属性、样式、节设置或表格布局。
2. `crates/tools/src/lib.rs` 和 `crates/chat/src/lib.rs` 的 Word 路由主要暴露 `read_docx`、`edit_docx`。用户提出“统一字体、行距、表格宽度”时，模型没有对应的专用操作。
3. 内置 `md_to_docx.py` 使用 `Document()` 新建文档，并在多个位置设置宋体、10.5 pt、1.15 倍行距等直接格式。表格默认采用 Table Grid，尚未接通可复用的样式模板、成熟 writer 和页面验收链路。
4. 交底、申请与审查意见分别携带转换器，文件并不完全相同；提取公共逻辑时必须保留各入口的业务差异。
5. 已有 DOCX 测试验证文字、OMML 和未修改包部件的保留，不能证明分页、表格宽度及字体显示正确。此前文档明确记录 Word/LibreOffice 页面验收未完成。
6. 独立 Reviewer 的工具目前仍仅支持只读文本、搜索和文件列表，并拒绝二进制文件。它不能直接查看 DOCX 页面图片，视觉审查需要补充受控证据能力。

相关基线文档：`docx-editing-accuracy.md`、`chat-local-document-reading.md`、`word-editing-open-source-options.md`。

## 推荐实现

采用已核查的上游能力：新文档由 Pandoc + reference.docx 生成，固定表单按需使用 docxtpl，已有文档的常见格式通过 python-docx API 修改，分页和 PDF 导出交给本地 LibreOffice。Quarto 是在 Pandoc 基础上完成科学出版的实际先例，Gotenberg 是委托 LibreOffice 转换并维护真实文档回归集的实际先例；具体源码链接与边界见选型文档。

SomniQ 在共享 runtime/tools 中实现工具适配、对象定位、版本检查、审计和证据，Desktop 复用 PDF.js 展示结果，并接入现有 Executor → 独立 Reviewer → 修订循环。Markdown 解析、通用文档模型、TeX 到 OMML 转换、分页引擎均复用上游，新增代码聚焦产品接入。

```mermaid
flowchart LR
    A[用户要求与原稿] --> B[检查文档与解析排版要求]
    B --> C[选择模板并生成修改计划]
    C --> D[本地生成候选 DOCX]
    D --> E[Open XML 结构检查与 LibreOffice 渲染]
    E --> F[独立 Reviewer 审查]
    F -->|需要修订| C
    F -->|验收通过| G[预览与交付]
```

### 统一样式与模板

新文档以版本化 reference.docx 为样式来源，覆盖纸张、页边距、中西文字体、正文、标题层级、段前段后、行距、首行缩进、图表题注、页眉页脚、列表和公式。按 Pandoc 官方方法从默认 reference.docx 开始，在 Word 或 LibreOffice 中修改样式。SomniQ 只记录模板 id、版本、哈希、支持范围与必要的上游选项，不另外设计一套样式继承引擎。

新文档使用 Pandoc Markdown 或其现成 AST，段落、标题、列表、表格、图和公式由 Pandoc writer 输出。自定义段落和字符样式使用 Pandoc 的 custom-style。字体与段落规则主要由 Word 样式表达，减少逐个 run 写入重复直接格式；源内容到审查问题的定位信息由薄适配层保存。复杂题注、交叉引用和出版布局确有需求时，评估直接采用 Quarto 的渲染入口；同一任务固定一种后端，避免自行复刻其整套 filters。

Pandoc 的 reference.docx 只提供样式和文档属性，正文会被忽略。需要保留封面、固定表格和占位内容的机构表单，使用 docxtpl 在已有 DOCX 模板中填充字段；沿用其 Jinja2 规则、转义和模板检查，不把 reference.docx 当作可填表单。

已有文档采用“保留现有样式”或“按指定模板统一格式”的明确范围。前者只修改用户指定对象；后者先预览全局影响，处理直接格式覆盖模板样式的问题。格式统一应保留有语义的粗斜体、上下标和公式格式，不能笼统清除全部直接格式。

纸张与字体优先采用用户或模板要求；没有要求时，中文研究报告模板明确使用 A4，其他模板分别规定默认值。记录字体可用性和替代情况。缺少目标字体时，不能宣称已经验证目标环境的版式。

### 扩展受控格式操作

保留 `edit_docx` 的现有文字替换契约，新增独立的格式操作入口，建议名称为 `inspect_docx_format` 和 `format_docx`。入口是上游 API 的受控适配，不计算页面布局。常见样式、段落、节和列宽优先调用 python-docx 的公开 API；Open XML SDK 用于结构验证，复杂对象修改另按实际缺口评估。

以下是目标操作集，只有经回归证明可安全执行的操作才进入首批：

- 为选定段落指定已存在且合法的样式。
- 修改指定段落的对齐、首行缩进、段距、行距、与下段同页、孤行控制。
- 为明确选定的文本范围设置中西文字体、字号等直接格式。
- 修改明确选定节的页面尺寸和页边距。
- 修改既有表格的宽度、列宽、单元格边距、表头重复和允许拆行属性。

上述项目并非 python-docx 均有公开 API。中西文字体映射、表头重复和禁拆行等缺口单独列出，优先固化在模板，或采用经样本验证的上游 typed OOXML 操作；在验收前不宣称支持。必要的单项适配限制在明确属性，不扩展为通用 XML 编辑器。

格式操作不开放原始 XML 给模型。读取结果提供样式继承、直接格式、节和表格位置；对于不能可靠解析的有效格式返回“未知”。所有操作绑定输入文档哈希和对象定位；首次支持的格式批次不新增、删除或重排段落及表格，因此可以在固定结构上应用。后续结构编辑使用独立事务和新的定位方案。

候选稿先输出为副本，复用现有文件边界、锁、版本冲突、change ledger 和精确撤销机制。用户接受替换原稿前重新校验原稿哈希。表格布局改变也不能误改合并单元格、书签、关系或原生公式。现有 Rust 文字编辑保留未修改包部件；python-docx 保存可能重新序列化 XML，格式修改必须额外检查非目标内容、关系和保护对象，不能承诺未改 XML 字节完全相同。撤销通过保存的原始文件恢复。全局样式调整造成的重新分页在预览中显示。

带修订、域、数字签名或当前不支持的 OOXML 特性的文档，沿用明确拒绝或限定操作的方式。已有 DOCX 不经 Pandoc 转成 Markdown 再重建，避免上游已明确提示的有损往返。旧二进制 `.doc` 由 LibreOffice 在副本上转换后处理，另行检查转换差异；第一版优先保证 `.docx`。

### 优先修复表格和公式

表格采用 Pandoc 的列宽描述、模板的表格样式以及 python-docx 已支持的列宽/autofit 设置；实际排版由 LibreOffice 或目标编辑器完成。长表表头重复、短行完整显示、超高行拆分与合并单元格均纳入回归样本，不假定上游默认输出已经满足要求。宽表先使用明确列宽或获准的横向分节。

标题与后续内容、题注与图表通过段落属性保持合理关联。避免给整张长表或大量连续段落设置同页，造成大块留白。

新文档的数学公式优先走 Pandoc 已有的 TeXMath → OMML writer；现有自制转换器只保留为迁移期间的兼容路径，逐个业务样本对比后替换，不继续扩展成另一套通用数学转换器。增加公式段落样式、上下间距和行内基线验收。长公式断行、复杂 TeX 命令和带编号交叉引用按实际样本验证；第一阶段保证已有编号和引用不被破坏。用户要求可编辑公式时，图片或普通文本回退使该要求未通过。

### 本地渲染与证据

通过本地 LibreOffice headless 将候选 DOCX 转为 PDF，Desktop 复用现有 PDF.js 渲染为页面预览和证据图片。直接复用现成排版与 PDF 显示引擎。参考 Gotenberg 的独立 profile、启动就绪、超时、取消和自有进程回收设计；其当前实现基于受管 LibreOfficeKit helper，不能把容器代码直接视为 Windows CLI 实现。首版 Windows 适配直接调用本地 LibreOffice，只有已有本地 Gotenberg 服务时才按需接它的 API，不默认增加 Docker。

固定工具版本和字体环境，安装或下载组件通过明确的产品操作进行。每次任务使用独立临时目录、独立用户配置和受管进程树，支持超时和取消。docx-preview 可后续用于快速内容预览，但上游明确没有实时重分页，不承担最终页码与布局验收。

继续遵守现有 Word/WPS 会话保护：不附着用户的编辑会话、不结束用户的 Office 进程。Word/WPS 验收采用明确的独立验收环境或由用户打开副本；不能以给普通 Bash 增加 COM 例外的方式实现。

证据记录候选 DOCX 哈希、模板哈希、排版参数、字体环境、渲染器版本、PDF/PNG 哈希、页数、日志和对应修改计划。检查分为三类：结构完整性、明确格式规则、页面显示。自动规则检查只覆盖可以可靠测量的项目；溢出、遮挡、公式显示等还需要页面审查。

LibreOffice 结果仅代表该渲染环境。准备固定的 Word 与 WPS 打开、编辑、保存、重开验收样本，记录软件和字体版本。跨编辑器不要求像素相同，但必须满足相同的内容、可编辑性和排版约束。缺少某个目标编辑器的验收时，保留该项“未验证”。

### 独立审查与 Desktop 交互

Reviewer 接收用户原始要求、修改计划、结构与样式差异，以及当前候选版本的页面证据，不读取 Executor 的完整对话。宿主提供限定的只读文档证据和图片附件能力；只传项目内、已生成且哈希匹配的文件。

只有实际可用的视觉 Reviewer 看到所有要求验收的页面，才能给出视觉通过结论。长文档分批覆盖所有页面并记录覆盖范围。只有文本能力时可以完成结构审查，视觉验收保持未验证，允许用户手动检查页面；不能将结构通过显示成完整排版通过。

问题记录页码、对象或源块 id、严重性、依据和建议。Executor 据此修订并重新渲染。设置可配置的修订上限，建议默认三轮；达到上限、无进展或外部依赖缺失时保留候选稿与问题清单，准确报告未通过项。任何修改都会使旧页面与旧审查结论失效，必须重新绑定最终候选哈希。

Desktop 提供原稿/候选预览、样式修改列表、页码问题导航，以及“保留副本”“接受修改”“恢复原稿”等已有审阅语义。面向用户的状态使用“已生成”“已检查格式”“已检查页面”“需人工确认”等可理解的表达。技术参数保留在审计详情中。

## 技术选型与仓库落点

首版运行依赖收敛为 Pandoc、已有 python-docx 与本地 LibreOffice。Pandoc 是新文档默认后端；docxtpl 只在固定表单场景启用。Quarto 作为需要完整科学出版能力时的可选后端，不同时打包两套重复工具链。Open XML SDK 先用于开发/发布结构验收，不强制桌面用户增加 .NET；docx4j 作为 Java 技术路线的替代选项，不叠加进首版。

保留 Rust 的精确文字编辑、文件权限、版本与审计机制。内置技能保留业务入口和独立使用能力，调用版本化的上游适配入口；打包时提供明确的运行时位置、版本与许可证，避免依赖其他技能目录的相对路径。用户提供的模板和正文默认留在本地。

计划落点：

- `crates/runtime`：上游进程/API 适配、格式白名单、模板清单、受管渲染任务和证据状态。
- `crates/tools`：文档工具契约、权限与审计接入。
- `crates/chat`：中文“Word 排版、行距、格式统一”等意图的完整路由。
- `desktop/src-tauri`：渲染调度、独立 Reviewer 证据适配和本地 API。
- `desktop/src`：DOCX 候选稿页面预览、样式差异和接受/撤销交互。
- 内置文档生成脚本：保留业务入口，调用固定版本的 Pandoc 或指定表单后端。

ONLYOFFICE/Collabora 的完整可视化编辑器作为后续产品路线，评估离线部署、安装体积和许可证后单独决策。当前优先完成可重复的生成、修改与验收链路。

## 回归与完成定义

参照 Gotenberg 的真实文档 corpus + manifest 方法，记录每个样本的已知内容、固定标记、页面事实及其测量环境。上游的结构测试和简单转换成功不等于本项目的页面验收。引擎或字体升级时重新检查同一批样本，对变化解释原因。

测试集至少覆盖：中文与英文混排；直接格式覆盖样式；标题孤立；段落孤行；页眉页脚和多节；跨页长表；横向宽表；合并单元格；图片题注；行内与独立公式；修订/签名文档的明确拒绝；文件占用和外部并发修改。包含故意制造的缺陷，验证检查确实能发现问题。

按仓库要求运行受影响 crate 的聚焦测试，跨 crate 后运行 `cargo test --workspace`；Desktop 运行相关 Vitest 和 `npm run build`。补充结构/布局回归和指定渲染环境下的逐页检查；不能以测试数量替代目标文档验收。

交付通过需同时满足：用户排版要求有明确映射；正文、数字和公式内容未发生非预期改变；保护对象与包结构完整；约定环境的页面检查已完成；独立 Reviewer 或明确标注的人工验收记录已绑定最终 DOCX；可以回滚。已从用户提供的后台只读提取并核实原始用户请求，形成 [8 类请求验收标准](docx-user-acceptance.md)。原始附件仍不可得，使用脱敏衍生样本，不声称已定位客户具体文档的所有故障。

当前分支已接入 M1 的 Pandoc 模板化导出；M2 的 python-docx 段落/字符格式及显式锚点结构操作、odfpy 的 ODT 去高亮；M0 的受管 LibreOffice 渲染、版本证据和 Open XML SDK 结构验证。原生页码、书签/REF、编号、表格及图片经过公开样本验收，保留权限、审计、原字节撤销和 Chat 路由。复杂表格重构、任意节布局、客户原附件、全部领域脚本迁移、M3 独立视觉 Reviewer/Desktop 界面和 M4 目标编辑器兼容仍未完成。

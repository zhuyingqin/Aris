# 非 Reviewer 问题修复设计评估

日期：2026-10-26。依据[本地复核报告](recent-dialogue-audit-and-fix-plan-20261025.md)和当前源码；继续排除 Reviewer 专属问题。本轮未连接服务器，未修改应用源码，也未执行模型调用。

建议先交付**提示词完整性与最小诊断**，随后单独修复无效 revision 恢复；再处理当前任务、历史规则及项目意图更新；模型无通道处理可独立交付。确定性代码缺陷可以用本地测试确认，写作行为改善需要另做真实模型对照，不能用结构测试通过代替。

## 1. 优先级与实施边界

下表沿用审查报告的 A–F 编号，按推荐实施顺序排列。复杂度表示改动面与兼容风险，不代表工期承诺。

| 顺序 | 批次 | 建议交付 | 复杂度 | 结果的可验证性 |
| --- | --- | --- | --- | --- |
| 1 | A + F 的最小部分 | 核心规则始终装配；分段错误可见；缓存正确失效；输出本地 manifest | 中，跨 runtime/chat/desktop | 高：可用故障注入和最终请求捕获验证 |
| 2 | D | 无效 revision 分类并接入现有有界恢复 | 低到中，主要在 runtime 及工具错误出口 | 高：可以完整离线验证 |
| 3 | B | 当前请求约束动作；历史助手方法带来源和适用范围；文风行为回放 | 中，涉及模板、召回包装和模型行为 | 结构可测；语义效果须真实模型验证 |
| 4 | C | 意图推断批次明确；失败不消费水位；异步结果校验版本 | 中到高，涉及持久化与兼容迁移 | 高：引用、并发、窗口滑动均可离线验证 |
| 独立交付 | E | 无通道分类、冷却、单次恢复探测 | 中，共享执行器和状态展示 | 高：用模拟响应、时钟和并发验证 |
| 随后补齐 | F | 可导出的最小本地诊断包 | 低到中，复用现有 trace | 高：超限输入和脱敏夹具可验证 |

A 优先是因为它会使后续行为约束失效；D 可作为范围小、验证明确的独立修复。B 与 C 分开提交，便于区分“模型按错方法执行”和“持久状态更新错误”。

## 2. A：保证基础规则，不让可失败的加载吞掉整套提示词

源码已具备可复用基础：[SystemPromptBuilder::build](../../crates/runtime/src/prompt.rs#L159) 从编译内置模板开始构建，不需要先成功读取项目或配置。实际整套失败发生在 [load_system_prompt](../../crates/runtime/src/prompt.rs#L793) 的前置读取，再由 [Desktop fallback](../../desktop/src-tauri/src/system_prompt.rs#L253) 静默丢弃。

建议这样改：

1. 在 runtime 建立一个分段构建入口，先生成基础模板、环境和任务范围等内置规则，再分别加载项目指令、配置、技能等动态部分。加载失败返回段落状态与原因，已成功部分保留。
2. 建议返回 `PromptBuildReport`，含 `sections`、`issues`、`inputFingerprint` 和 `cacheable`；段落具有稳定 ID。原有严格 Result 接口可作为兼容包装，共用同一构建逻辑。
3. [共享 chat 装配](../../crates/chat/src/lib.rs#L140) 始终追加产品身份、语言和 Desktop 附加规则，并传递构建状态。Desktop 消费带状态的结果，移除 access-only fallback。CLI 复用相同底层构建，避免维护第二套基础文本。
4. 项目指令逐文件读取并标记失败，区分“文件不存在”和“文件存在但不可读”。必要约束不可读时明确报告缺失，允许检查与恢复；依赖未知约束的修改不能当成正常完整环境继续。工具权限仍由现有权限运行时决定。
5. 使用同一份输入快照计算指纹与构建内容，防止先算缓存键、再读到另一版本。缓存键纳入有效配置版本/指纹，保留已有指令指纹；不把降级结果作为正常缓存。文件修复后下一轮应恢复。

首批同时写入有界 `prompt.built` 本地事件：构建版本、段落状态、指纹、错误类别、session/turn。错误状态可去重显示，正常聊天不增加交互步骤。

**验收：**无效 UTF-8 指令文件、损坏配置、读取失败分别注入；基础与 Desktop 附加规则仍在，错误可定位；恢复输入后不复用旧降级结果。通过捕获最终请求验证 Chat 和 Responses 两种编码，不能只检查构建器返回值。权限失败应由可注入读取器稳定模拟，避免测试依赖本机管理员权限。

## 3. D：复用已有恢复器，补上 revision 格式错误

[文件校验](../../crates/runtime/src/file_ops.rs#L1091) 已能正确拒绝 63 位哈希；格式错误目前是普通 InvalidInput 文本，而版本冲突已有结构化 `revision_conflict`。应保留这项校验。

建议在文件工具错误出口给格式错误提供稳定的 `code=invalid_revision`、目标路径、`retrySameArguments=false` 和重新读取提示。在 [ToolRecoveryState](../../crates/runtime/src/tool_recovery.rs#L62) 增加对应分类，优先识别错误码，并为旧错误文本保留有限兼容。

复用现有“相同请求失败两次，阻止第三次原样调用”的机制；描述或 timeout 改动不算纠正，重新读取也不应清除该失败记录。复制正确 revision 后参数已改变，应允许执行。格式错误、内容版本冲突和旧锚点失配分别处理；冲突时重新阅读内容，不能直接抄错误中的当前哈希继续旧编辑。

**验收：**63 位哈希无写入；第三次原样请求被阻止；改为读取结果中的正确 64 位哈希后可执行；压缩上下文后仍保留未解决的失败记录。验证真实工具返回及恢复器串联结果，不能只对错误字符串做单元测试。

## 4. B：约束方法与规则来源，保留正常自主执行

[基础提示词](../../crates/runtime/assets/prompts/system.md#L44) 已有任务范围和最新上下文规则；[召回头部](../../desktop/src-tauri/src/memory.rs#L34) 也已有“不作为指令”的声明。因此只追加同义提醒，预计收益有限。

建议分两步实施：

- **先修当前规则的表达和装配。**用简洁的通用规则区分用户要求、助手提出的方法和实际验收条件。文风比较应以对应段落的措辞、句子作用、论证组织及具体改写为依据；数字统计须说明它服务的判断，不能自动成为写作质量标准。用户追问方法选择时，回答现有证据能够支持的原因与不确定性。
- **再修历史信息的包装。**复用已有角色、session 和来源信息，把助手历史建议标为派生方法，并表达其适用任务。历史记录真实不等于它对当前任务有指令权威；已有用户确认的稳定偏好仍可正常沿用。优先改召回渲染和已有规则持久化入口，不要求首批迁移整个记忆库。

不以“为什么”等词建立硬编码工具开关，也不为每轮额外增加一次模型分类调用。是否需要分析、修改或继续执行，应以用户完整请求和上下文为准。明确的继续请求仍应保持工作连续性。

**行为回放至少包含这些成对场景：**

| 输入 | 应观察到的行为 |
| --- | --- |
| “逐段对照参考文风、用词、写法” | 给出具体段落判断与改写依据；不会仅以符号频率证明改好 |
| “为什么你选择这些指标” | 解释方法选择的可见依据；不自动转入新一轮统计或假称知道原模型内部原因 |
| “统计两份文档中破折号的数量” | 正常完成计数 |
| “为什么这个函数出错，顺便修复” | 可以检查和修改相关代码 |
| 相同任务带旧助手“先量化句法”片段 | 旧方法有来源，不能覆盖本轮明确要求 |
| 明确“继续改下一段” | 沿用已确认的段落任务和输出位置 |

先制作脱敏最小上下文与预期行为；结构测试验证来源、角色和提示词组成。语义对照须记录模型版本、上下文和采样条件，检查实际答复及工具动作；mock 通过不能证明模型行为已改善。本轮不调用模型做这项验收。

## 5. C：把意图推断结果、处理水位和状态版本分开

[当前状态](../../crates/runtime/src/project_intent.rs#L97) 使用滚动证据数组及 count；[推断调用](../../desktop/src-tauri/src/engine.rs#L5265) 又把失败转换成 None。当前任务能否得到正确响应，不能依赖长期项目意图先成功换向。

建议先修契约，再处理持久化：

1. 推断输入分别列出旧支持证据和本批新增 USER 证据，显式提供可用于改向的 ID。输出也分开历史支持引用与新改向引用。
2. 在应用层区分“有效无变化”“有效提案”“引用不合法”“推断失败/取消”。仅处理成功的批次推进完成水位；失败和无效提案保留待处理证据，并用批次指纹与有界退避防止每次刷新立即重算。
3. 对三条有效新引用加一条已知旧支持证据的情况，校验并单独计算有效新引用；未知 ID、助手引用和不支持目标的证据应明确拒绝。保持“至少三条一致 USER 改向证据”等长期目标保护，不靠降低门槛解决。 ID 与数量校验只验证引用资格；语义一致性仍须结合原文判断，并在回放中单独核验，不能把三条任意新消息当成持续改向。
4. 把处理基线逐步迁移为稳定证据 ID/单调序号，并增加状态版本。推断绑定原始批次和版本，应用时在项目级同步保护下检查；出现新状态时保留新证据，旧结果不能覆盖它。
5. 为旧文件做带 schema version 的兼容迁移，保留 objective、支持证据与原始备份。已有历史不足的部分保持未知，不批量重新推断或改写所有项目目标。

**验收：**重放已有三组引用；测试有效无变化、无效引用、解析失败、取消；检查失败后水位不前移、同批不紧密重试。覆盖两会话并发追加、24 条窗口滑动、证据排序与旧异步结果晚到。当前用户请求的处理不等待长期意图累计足够证据。

这部分涉及持久化，建议单独提交和回滚；仅把 `.all()` 改成宽松计数，无法解决失败消费水位和过期结果覆盖。

## 6. E：按错误原因决定重试与恢复

[执行器](../../crates/executor/src/openai.rs#L2371) 当前按 HTTP 状态确定通用重试。应在读取错误正文后、进入通用 503 重试前，先做共享错误分类。

- 优先使用上游结构化 code/type；缺少稳定字段时，只对明确的 `No available channel` 响应做兼容识别。普通 503、限流、暂时过载、鉴权和网络错误分别处理。
- 已确认无通道时结束当前无效重试簇，记录临时冷却。状态按标准化端点、模型和凭据/配置代次隔离；使用内部标识，不保存凭据。
- 冷却结束后只允许一个恢复探测，其他相同请求复用该状态；探测成功清除冷却，仍失败则有界退避。配置更新或用户明确重试也可触发恢复检查。
- 通用请求、重启路径及 Chat/Responses 适配复用同一分类和状态；取消应及时结束等待。按现有明确配置处理备选模型，并显示实际使用状态。

**验收：**模拟本轮错误，校验当前调用不会再完整重试，后续同配置调用不重复簇；并发恢复只发生一次探测。其他模型、账号不受影响；暂时性错误仍可恢复；更新配置和取消路径正常。冷却的初值、上限和 Retry-After 行为作为可配置策略确定，不把历史失败解释成永久下线。

## 7. F：在本地补足可定位信息

已有 [llm.request trace](../../crates/executor/src/openai.rs#L2277)，可以复用其关联和落盘机制；新增独立、有界的 prompt manifest，避免诊断字段依赖整段请求正文成功留存。

建议保留构建版本、session/turn/attempt、用途、模型、配置代次、prompt manifest ID、段落状态与指纹、压缩代次、正文大小与省略原因。A 的构建事件与实际发送事件使用同一 manifest ID，能够判断问题发生在加载、装配还是最终编码阶段。

本地诊断包只包含必要元信息、错误分类和用户选择的脱敏片段；正文超限时这些元信息仍保留。用真实超限形状的夹具校验两种端点和导出结果。服务器归档增强可作为其他仓库的后续事项，不是完成上述修复的前置条件；本次原轮输入缺失无法靠新增日志补回来。

## 8. 交付与验证方式

每批提交包括对应最小故障夹具、改动、验证结果与兼容说明。A 的构建和缓存测试、D 的工具恢复、C 的状态并发、E 的错误响应与时间推进均可在本地完成。语义行为回放单独记录真实模型结果，避免把“程序路径正确”和“模型回答改善”混成一个结论。

按仓库要求先运行变更 crate 的聚焦测试；跨 crate 改动再运行 `cargo test --workspace`。Desktop/Tauri 接口变化运行聚焦 Vitest 和 `desktop/` 下的 `npm run build`。持久化迁移先保留原文件，验证读旧/写新和回滚路径。

本轮完成的是修复设计评估，未运行应用回归测试，未证明任何修复已生效。原审查报告与本地证据清单保持原样，方便分别核对“已发生的问题”和“待实施的设计”。
